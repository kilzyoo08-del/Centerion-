# Centerion — единая карта системы

Этот документ фиксирует одну архитектуру проекта и убирает разрозненные точки подключения.

## 1. Источник истины

- **GitHub `kilzyoo08-del/Centerion-`** — единственный основной репозиторий приложения и backend-кода.
- **Android** — Kotlin + Jetpack Compose из GitHub. Flutter-копию в Deepnote не развиваем параллельно, пока не принято отдельное решение о миграции.
- **Centerion API** — единственная серверная точка входа для Android.
- Секреты хранятся только в серверных настройках. В APK допускаются только публичные параметры Supabase.

## 2. Роли сервисов

| Сервис | Единственная роль | Не использовать как |
|---|---|---|
| GitHub | Исходный код, review, CI и сборки APK | Хранилище секретов в коде |
| Supabase | Auth, пользовательские данные, долговременная память, задания и Edge Function `centerion` | Вычислительный сервер или LLM |
| Deepnote | Разработка, тесты, эксперименты и исследовательские вычисления | Постоянный публичный API-хост |
| PostHog | Ошибки, события, производительность и продуктовая аналитика | База данных или AI runtime |
| Centerion API | Маршрутизация запросов к ядрам и worker-задачам | Клиент с привилегированными ключами |

## 3. Единый путь запроса

1. Android получает сессию через Supabase Auth.
2. Android отправляет запрос на публичный endpoint Centerion с пользовательским JWT.
3. Edge Function `centerion` проверяет JWT и получает идентификатор пользователя из проверенной сессии. Идентификатор владельца нельзя принимать как доверенное поле от Android.
4. Edge Function передаёт запрос на настроенный Centerion API/runtime.
5. Orchestrator выбирает нужное ядро: chat, files, code, memory или compute.
6. Постоянные пользовательские данные сохраняются в Supabase с проверкой владельца.
7. События без содержимого личных сообщений отправляются в PostHog.
8. Тяжёлые тестовые/исследовательские задачи можно запускать в Deepnote; пользовательский API не должен зависеть от работающей вкладки ноутбука.

## 4. Единые контракты

- Android знает только базовый HTTPS URL Centerion и публичную конфигурацию Supabase.
- Android не знает адреса Deepnote, внутренние адреса worker, service-role key, PostHog secret или ключи runtime.
- Backend получает конфигурацию из переменных окружения: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (только на сервере), `POSTHOG_HOST`, `POSTHOG_PROJECT_KEY` (только на сервере), `CENTERION_RUNTIME_URL`, `CENTERION_RUNTIME_TOKEN`.
- Если runtime не подключён, API честно возвращает `503 model_unavailable`; нельзя имитировать полноценный ответ.
- Если отдельное ядро не настроено, его endpoint сообщает об этом явно (например, vision — unavailable), а не выдаёт фиктивный результат.

## 5. Что уже найдено и что блокирует полное соединение

- Supabase Edge Function `centerion` существует и включена с JWT verification. Это подходящая публичная точка входа, но upstream runtime должен быть настроен и проверен.
- В основной ветке Android API всё ещё содержит временный ngrok URL. Его нужно заменить конфигурацией единого HTTPS endpoint.
- Backend в основной ветке использует локальную SQLite для истории и памяти; это не согласовано с Supabase и не подходит для постоянного публичного сервиса без постоянного диска.
- Backend adapter содержит старый путь модели `/kaggle/working/centerion_qwen3_4b`. Это legacy-конфигурация, а не доказательство запущенного Centerion runtime. До выбора и проверки собственного inference runtime чат должен оставаться явно недоступным.
- `POST /media` в основном backend пока отвечает 501: полноценное распознавание изображений не подключено.
- Deepnote-проекты остановлены; Deepnote используется как среда разработки/экспериментов, а не как постоянно доступный сервер.
- PostHog-проект существует, но ранее в нём не было событий за последние 30 дней. Нужно добавить и проверить отправку событий.
- В Supabase ранее обнаружены избыточные прямые grants, включая TRUNCATE для клиентских ролей. Перед публичным выпуском применить только проверенную миграцию с ограничением прав и повторно проверить RLS.
- PR #3 содержит Android Auth/API и память, но не объединён с main и требует разрешения конфликтов/CI.
- PR #7 содержит ограниченный планировщик задач на CPU хоста; это не гипервизор и не отдельная виртуальная машина. Он должен подключаться как один из backend-модулей после тестов.

## 6. Порядок завершения интеграции

1. Свести Android к одному Kotlin-клиенту и удалить зависимость от временного ngrok URL.
2. Зафиксировать контракт Android → Supabase Edge Function `centerion` → Centerion runtime.
3. Подключить runtime к Supabase для памяти и задач, сохранив owner-scoped доступ.
4. Добавить PostHog server-side события без текста сообщений, файлов и секретов.
5. Подключить Deepnote как среду проверки/worker только для задач, которые допускают задержку; не делать его обязательным для чата.
6. Исправить security grants, проверить JWT/RLS, rate limits и изоляцию двух аккаунтов.
7. Пройти backend tests, Android unit tests и end-to-end проверки; только после этого собирать APK.

## 7. Правила безопасности

- Никогда не добавлять service-role key, runtime token или PostHog secret в Android, Git или публичный notebook.
- Не открывать Android доступ к `kolai-bridge`; у него отключена стандартная JWT-проверка, и он не является публичным API приложения.
- Не выполнять SQL security migration и не менять production secrets без отдельной проверки.
- Не считать PR, notebook или сохранённый отчёт подтверждением работающего production-сервера: проверять живой endpoint и реальные end-to-end запросы.

**Цель:** одна Android-версия, один API-контракт, один источник кода и чёткое разделение ролей сервисов.
